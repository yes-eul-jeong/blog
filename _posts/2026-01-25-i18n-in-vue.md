# Vue3에서 `<i18n-t>` 사용 시 발생한 문제 정리

<br/>
## 1\. 문제 배경

Vue3 프로젝트에서 `vue-i18n`으로 다국어 처리를 하고 있었다.  
단순 문자열이 아니라 문장 중간에 스타일이 적용된 값(숫자)을 삽입해야 하는 요구사항이 있었다.

예시 UI:
{% raw %}
```
<h3 class="title-s">
  총 <span class="blue-txt">{{ totalCnt }}</span>건
</h3>
```
{% endraw %}

<br/>

이를 다국어로 처리하기 위해 메시지를 아래와 같이 정의했다.

```
{
  "total_count": {
    "title": "총 {count}건"
  }
}
```

* * *

## 2\. `<i18n-t>`를 사용한 시도

vue-i18n 공식 문서에서 제공하는 컴포넌트 방식인 `<i18n-t>`를 사용하면  
slot을 통해 동적 값을 삽입할 수 있다고 판단했다.

<br/>

```
<h3 class="title-s">
  <I18nT keypath="title.total_count.title" tag="span">
    <template #count>
      <span class="blue-txt">{{ totalCnt }}</span>
    </template>
  </I18nT>
</h3>
```

* * *

## 3\. 발생한 문제

렌더링 시 아래 에러가 발생했다.

```
[intlify] Not found parent scope. use the global scope.
```

혼란스러웠던 점:

- Vue3 사용
- `legacy: false`
- `main.js`에서 i18n 정상 등록
- `$t()` / `useI18n()`은 정상 동작
- **같은 부모를 공유하는 컴포넌트 중** **`<i18n-t>`를 사용하는 특정 컴포넌트에서만 에러가 발생**

* * *

### 4\. 원인 분석: `useI18n()`을 썼는데 왜 못 찾을까?

분명 해당 컴포넌트의 `script` 영역에서 `useI18n()`을 호출했고, 심지어 전역 설정을 참조하도록 선언했다.

<br>

```
// 컴포넌트 내부 script
const { t } = useI18n({ useScope: 'global' }); // 전역 스코프를 쓰겠다고 선언
```

스크립트에서 `t()` 함수는 전역 메시지를 잘 가져왔다. 하지만 템플릿의 `<i18n-t>`에서는 여전히 동일한 경고가 발생했다. 원인을 파헤쳐 보니 **`useI18n()`이 관리하는 스코프와 `<i18n-t>` 컴포넌트가 스코프를 찾는 방식이 서로 독립적**이기 때문이었다.

- **`useI18n()` (Script 영역):** 호출 시 해당 컴포넌트의 JS 실행 컨텍스트에 i18n 기능을 주입한다. 여기서의 `useScope: 'global'`은 `t()` 함수가 메시지를 찾는 범위를 결정할 뿐이다.
- **`<i18n-t>` (Template 영역):** 렌더링 시점에 Vue의 컴포넌트 트리(계층 구조)를 따라가며 i18n 주입 상태를 탐색한다.

* * *

## 5\. `useScope: 'global'`으로 해결되지 않았던 이유

`useI18n`의 옵션은 **Script 레벨**의 참조 범위만 지정할 뿐, **Template 레벨**에서 컴포넌트 형태로 쓰이는 `<i18n-t>`의 탐색 로직에는 간섭하지 않는다. 

즉, 스크립트에서 아무리 "전역을 쓰겠다"고 선언해도, 템플릿에 놓인 `<i18n-t>` 컴포넌트는 다음과 같은 과정을 거친다.

1. 현재 컴포넌트에 별도의 `<i18n>` 로컬 블록(Local Scope)이 있는지 확인한다.
2. 없다면 부모 트리로 올라가며 탐색한다.
3. 명시적인 스코프를 찾지 못하면 **"\[intlify\] Not found parent scope"** 경고를 띄우고 마지막 수단으로 글로벌을 사용한다.

결국 **스크립트에서의 스코프 선언과 템플릿 컴포넌트의 스코프 선언은 별개**로 이루어져야 한다는 것이다. ~~한참을 골머리 썩히다 모든 AI모델들에게 다 물어보다 제미나이가 알려줬다.~~ 

<br>
{% raw %}
| **구분** | **useI18n({ useScope: 'global' })** | **`<i18n-t scope="global">`** |
| --- | --- | --- |
| **영향 범위** | `setup()` 내부, `t()` 함수 호출 시 | `<template>` 내 컴포넌트 렌더링 시 |
| **해결 대상** | Script 내 번역 로직 참조 오류 | \[intlify\] Not found parent scope 경고 |
{% endraw %}

<br>

## 6\. 최종 해결 방식: `<i18n-t>`에 `scope="global"` 명시

```
<!-- <i18n-t>에 직접 scope를 명시하기 -->
<h3 class="title-s">
  <I18nT
    keypath="title.total_count.title"
    tag="span"
    scope="global"
  >
    <template #count>
      <span class="blue-txt">{{ totalCnt }}</span>
    </template>
  </I18nT>
</h3>
```

<br>

이렇게 수정한 결과:

- `[intlify] Not found parent scope` 경고 제거
- 기존 컴포넌트 구조 유지
- `<i18n-t>`의 slot 기반 치환 방식 그대로 사용 가능
- 전역 메시지 사용 의도가 코드에 명확히 드러남


global을 사용여부를 template레벨 내에서 명시하는 것이 해결책이었다. 정말 별거 아니었는데 이거때문에 몇시간을 버린건지…

* * *

## 7\. 왜 이 방식이 더 적절한 해결이었나

문자열 치환(`v-html`) 방식도 하나의 대안이 될 수는 있지만, 다음과 같은 단점이 있다.

- HTML 문자열을 번역 메시지에 주입해야 함
- XSS, escaping 관리 부담
- 마크업 구조가 메시지와 강하게 결합됨

반면 `<i18n-t>` + `scope="global"` 방식은:

- vue-i18n이 의도한 **구조적 다국어 처리 방식**
- slot을 활용한 안전한 마크업 삽입
- 언어 변경 시 반응성 유지
- 메시지와 UI 역할이 명확히 분리됨

<br>

* * *

## 8\. 결론

- `<i18n-t>`는 `t()`와 동작 방식이 다르다
- `useScope: 'global'`은 script 영역에만 영향을 준다
- `<i18n-t>` 사용 시, 전역 메시지를 참조한다면 `scope="global"`을 명시하는 것이 안전하다
- 컴포넌트 트리 구조가 복잡할수록 scope를 명확히 지정하는 습관이 중요하다
